    Running and Submitting Jobs on mechthild

    There are different job types you can use on mechthild. The resources are managed by SLURM Depending on the or your application, you have to write your own job file or select one from a template. In general, resources for a job can be allocated using one of the following tools:

    • sinteractive, to obtain an interactive job
    • sbatch, to submit batch jobs to the slurm
    • salloc and srun for fine tuned interactive jobs.

    If you want to run a job using sbatch, you need to create a jobfile which specifies the execution environment and the commands you want to run. The basic template for this file looks like:

    #!/bin/bash
#SBATCH OPTION1
#SBATCH OPTION2 
#SBATCH .... 

# load your modules 
module load ....

# run the application
./app

    Download: basic_job.sh.

    All lines beginning with #SBATCH are interpreted by the resource manager and used to specify the environment. The options given after #SBATCH are the same that can be passed to sinteractive, sbatch, salloc or srun at the command line.

    The job file is submitted to the resource manager via 

    sbatch <OPTIONS> jobfile

    where <OPTIONS> can be further options that are not specified in the jobfile. If everything is specified in the jobfile neglect the <OPTIONS> argument.

    Common Options for Job Submission

    Every line in the jobs file which begins with #SBATCH is interpreted by the resource manager slurm. So all things after #SBATCH will be used like command line arguments of sbatch or sinteractive. For detailed information see the man page of sbatch. The most common parameters and options are shown in the table below.

    Input/Output
    -J NAME or --job-name=NAME Specify the name of the job. Used to identify the job later on.
    -i FILE or --input=FILE standard input file. If none is specified, ''/dev/null'' is used.
    -o FILE or --output=FILE Path to the file where standard output is redirected. Special placeholders for job id (%j), the execution node (%N), and the job name (%x) are allowed. The default file name is "slurm-%j.out", where the "%j" is replaced by the job ID.
    -e FILE or --error=FILE Path to the file where standard error output is redirected. Special placeholders for job id (%j), the execution node (%N), and the job name (%x) are allowed. If not specified the file for the standard output is used.
    -D DIRECTORY or --chdir=DIRECTORY Set the working directory of the batch script to directory before it is executed. The path can be specified as full path or relative path to the directory where the command is executed. Default: The current working directory.
    Notification
    --mail-user=xxx@mpi-magdeburg.mpg.de notifications will be sent to this email address. This must be an institute email address!
    --mail-type=FAIL,BEGIN,END notifications on different events: BEGIN ... begin, END ... end, FAIL ... failure/aborted, ALL ... all events. NONE ... no mail (default). Do not forget to specify the email address if you want to get these notifications.
    Resources/Queues
    -p PARTITION or --partition=PARTITION select the partition (formerly named queue), where the job is submited to. For details see Partitions
    -t DD-HH:MM:SS or --time=DD-HH:MM:SS Upper limit for the runtime of the job for better scheduling. The maximum time limit of the partition cannot be overwritten with this options.
    --mem=SIZE Specifies the memory required on every node for the job. Default in unlimited.
    --mem-per-cpu=SIZE
    -n NTASKS or --ntasks=NTASKS Request to launch the job using NTASKS tasks. The default is one task per cpu coreq, but note that the --cpus-per-task option will change this default.
    -c CPUS or --cpus-per-task=CPUS Advise the resource manager that ensuing job steps will require CPUS number of processors per task. Without this option, the controller will just try to allocate one processor per task. This is required for OpenMP or Hybrid OpenMP/MPI jobs.
    -N NODES or --nodes=NODES Request at least NODES nodes for the job. If -Nis not specified, the default behavior is to allocate enough nodes to satisfy the requirements of the -n and -c options. If neither -N, -n, -c is specified one cpu core on a single node is used.
    --exclusive=user Use the allocated nodes exclusively, if there are free CPU cores.
    -C LIST or --constraint=LSIT Specify a list of features that the allocated nodes must fulfill. Only nodes having features matching the job constraints will be used to satisfy the request. This is necessary to attach a bigmem node or the faster GPU nodes'''. Details see below.
    --nodelist=NODENAME,NODENAME,... Specify a list of nodes used for the job. If the nodes are not free the job will be queued. Use this option only if there is a good reason to select a special node, e.g. licensed software.
    --x11 Support for X11 forwarding. This is required for GUI applications like MATLAB

    Requestable Features

    Using the -C or --constraint option one can select nodes with special features. The man page entry describes the following for this 

    -C, --constraint=<list>
              Nodes  can have features assigned to them by the Slurm administrator.  Users can specify which of these features are required by their job
              using the constraint option.  Only nodes having features matching the job constraints will be used to satisfy the request.  Multiple  con‐
              straints  may  be specified with AND, OR, matching OR, resource counts, etc. (some operators are not supported on all system types).  Sup‐
              ported constraint options include:

              Single Name
                     Only nodes which have the specified feature will be used.  For example, --constraint="intel"

              Node Count
                     A request can specify the number of nodes needed with some feature by appending an asterisk and count after the feature name.   For
                     example  "--nodes=16  --constraint=graphics*4  ..."  indicates that the job requires 16 nodes and that at least four of those nodes
                     must have the feature "graphics."

              AND    If only nodes with all of specified features will be used.  The ampersand is  used  for  an  AND  operator.   For  example,  --con‐
                     straint="intel&gpu"

              OR     If  only  nodes  with  at least one of specified features will be used.  The vertical bar is used for an OR operator.  For example,
                     --constraint="intel|amd"

    In our setup the following features/constraints are available:

    Constraint Description
    4110 or XEONSILVER Select a node with a Xeon Silver 4110 CPU
    6130 or XEONGOLD Select a node with a Xeon Gold 6130 CPU
    7452 or AMD Select a node with a AMD Epyc 7452 CPU
    XEON8562Y+ or Intel Select a node with Intel Xeon Platinium 8562Y+
    RAM192 Select a node with a 192 GB Memory
    RAM384 Select a node with a 384 GB Memory
    RAM512 Select a node with a 512 GB Memory
    RAM768 Select a node with a 768 GB Memory
    RAM1500 Select a node with a 1536 GB Memory

    GPU Jobs

    We have three different type of GPUs in use. In the old GPU nodes we have ten NVidia P100 accelerators available, two in each node. On the newer GPU nodes we have twelve NVidia A100 GPUs and 28 Nvidia H100 accelerators available, either two or four available in the nodes.

    The GPUs can be requested with one of the following options in combination with the gpu partition.

    Option Description
    --gpus=TYPE:AMOUNT The job requires a total AMOUNT of GPU's of the desired TYPE. The TYPE is either P100, A100, or H100 and the AMOUNT is the overall number of GPUs required for the job. If TYPE is neglected and only an amount is specified, SLURM selects the desired number of free GPUs regardless of their type.
    --gpus-per-node=TYPE:AMOUNT Specify the number of GPUs required for the job on each node included in the job's resource allocation.
    --gpus-per-socket=TYPE:AMOUNT Specify the number of GPUs required for the job on each socket included in the job's resource allocation.
    --gpus-per-task=TYPE::AMOUNT Specify the number of GPUs required for the job on each task to be spawned in the job's resource allocation.

    If you want so start a job on a single NVidia P100 GPU you have to specify

    -p gpu --gpus=P100:1

    In order to obtain one of the NVidia A100 GPU nodes use

    -p gpu --gpus=A100:1

    To improve the scheduling of the GPU jobs and to avoid idle GPUs, please specify the required memory for your job using the --mem=, --mem-per-cpu= or --mem-per-gpu= option.

    Interactive Jobs

    Interactive jobs will be run with the sinteractive command, which is a wrapper around salloc and srun. The command line parameters are the same like you can use in the jobfile for a batch job. A interactive session is started with shell sinteractive <OPTIONS>

    Array Jobs and Parallel Jobs

    When the same operations have to be performed on a number of input arguments, an array job or a parallel job can be helpful. Both features can be used at once. An array job is created using e.g.

    sbatch --array=0-11:2%3 jobfile # or, equivalently
sbatch --array=0,2,4,6,8,10%3 jobfile

    which will schedule jobfile a total of 6 times, having the environment variable SLURM_ARRAY_TASK_ID set to the values 0, 2, ..., 10 and running at most 3 jobs simultaneously. Ue SLURM_ARRAY_TASK_ID variable in the jobscript to select e.g. input data or an algorithm.

    A parallel job is created by sending a job task to the background, e.g. via

      # inside job file
  srun -J 1 -n1 echo 1 &
  srun -J 2 -n1 echo 2 &
  srun -J 3 -n1 echo 3 &
  srun -J 4 -n1 echo 4 &
  wait

    Note the ampersand &> which creates a background process in bash, and the wait which blocks until all such processes finished. It is recommended to give each job step a name using -J. If you need more than a few parallel tasks, e.g. when using a bash for loop, or when requesting, say, more than 20 tasks more than allocated, use e.g. xargs to limit the number of parallel tasks created at once. This lowers the burden on the scheduling system (Slurm).

      # inside job file
  seq 4 | xargs -I% -P2 srun -J % -n1 echo % || true

    Note the absence of the ampersand. This example is equivalent to the previous one, except that it will only create (and therefore schedule/run) two job steps at once instead of all four. The -I% argument tells xargs to replace all occurrences of % by the current input, which is needed in this case to use the input twice: as arguments to srun as well as echo. The trailing || true< allows individual inputs to fail (determined based on their exit codes). Which inputs failed may be determined as follows.

    sacct -j JOB_ID --format JobName%30,State

    Job Management

    Job Status

    To see status of partitions and nodes, use

    sinfo

    To get the status of all SLURM jobs

    squeue

    To get the status of all personal SLURM jobs 

    sjobs

    To only view the jobs in the a partition

    squeue -p <PARTITIONNAME>

    Get the status of an individual job

    scontrol show job <JOBID>

    Job Cancelation

    To cancel a job, use scancel. You need the running or pending jobid. It is only the job's owner and SLURM administrators that can cancel jobs.

    scancel <jobid>

    To cancel all your jobs (running and pending) you can run

     scancel -u <username>

    Job dependencies

    A job can be given the constraint that it only starts after another job has finished. In the following example, we have two Jobs, A and B. We want Job B to start after Job A has successfully completed.

    First we start Job A by submitting it via sbatch:

    sbatch <jobA.sh>

    Making note of the assigned job ID for Job A, we then submit Job B with the added condition that it only starts after Job A has successfully completed:

    sbatch --dependency=afterok:<jobID_A> jobB.sh

    If we want Job B to start after several other Jobs have completed, we can specify additional jobs, using a ':' as a delimiter:

     sbatch --dependency=afterok:<jobID_A:jobID_C:jobID_D> jobB.sh

    We can also tell slurm to run Job B, even if Job A fails, like so:

     sbatch --dependency=afterany:<jobID_A> jobB.sh

    Updating jobs

    If the specified time limit of a job is too small is can be updated using 

    scontrol update jobid=JOBID TimeLimit=DD-HH:MM:SS

    Shared Memory Parallel Code -- OpenMP -- Single Node

    The following job file starts a job on a single node using all CPU cores.

    #!/bin/bash
# Your job name.
#SBATCH -J TESTJOB
#
# Output files. .out. is for standard output .err. is for the error output. 
#SBATCH -o %x-%j.out-%N # name of the stdout, using the job name (%x), the job number (%j) and the first node (%N)
#
# Maximum expected runtime.  ( 00 Days, 1 hour, 00 minutes, 00 seconds) 
#SBATCH --time=00-1:00:00   
#
# Allocate one node with all 16 CPU cores 
#SBATCH --nodes=1
#SBATCH --cpus-per-task=16 
#
# Choose Partition (Queue) 
#SBATCH --partition short 
#
# Mail Options 
#SBATCH --mail-type=FAIL,BEGIN,END    # An email is sent on begin, end, and failure of the job 
#SBATCH --mail-user=xxx@mpi-magdeburg.mpg.de   # E-Mail for notification
#
#SBATCH --exclusive=user
#
### END OF THE SLURM SPECIFIC PART ###

# Setup OpenMP 
if [ -n "$SLURM_CPUS_PER_TASK" ]; then
  omp_threads=$SLURM_CPUS_PER_TASK
else
  omp_threads=1
fi
export OMP_NUM_THREADS=$omp_threads

# load the modules system 

module load ...

    Parallel Job / Job Pack

    The following job file may be used as a benchmark runner both on a local machine as well as a Slurm job file. Inside a Slurm allocation, the parallelism is limited to the number of nodes requested using xargs -P$SLURM_NNODES, otherwise only one benchmark is run at a time. Note that this job file can be scheduled onto however-many nodes are requested, e.g. sbatch -N1 jobfile or sbatch -N100 jobfile.

    #!/bin/bash
#
# <YOUR LICENSE HEADER>
#
#SBATCH -J damn
#SBATCH -c 16
#
#SBATCH -N 10
#SBATCH -t 4:00:00
#SBATCH -p medium

set -eu

if [ ${SLURM_JOB_ID+x} ]
then
  echo level=info message=\"running inside Slurm allocation\" jobid=$SLURM_JOB_ID >&2
  module load compiler/gcc/10
  module load libraries/ufget/1.1.1
  module load libraries/mkl/2021.1
  # Pass -m to doctest for minimal output:
  run_benchmarks() {
    # First arg: benchmark executable
    # Second arg: matrix name (from xargs' stdin)
    # Remaining args: as given by user
    xargs -P$SLURM_NNODES -I% \
      srun --exclusive -n1 -N1 -J %/nnz$DAMN_CONFIG "$1" % "${@:2}" -m || true
    # Allow failures using `|| true`
  }
else
  echo level=info message=\"running locally\" hostname=$(hostname) >&2
  run_benchmarks() {
    xargs -P1 -I% "$1" % "${@:2}" -m || true
  }
fi

# Set defaults
export DAMN_DATA="${DAMN_DATA:-.}"

# Select matrices to benchmark; create list if necessary
MATRICES_FILE=$DAMN_DATA/matrices.txt
[ -f "$MATRICES_FILE" ] || path/to/list_matrices > "$MATRICES_FILE"

# Benchmark matrices
DAMN_CONFIG=16 run_benchmarks path/to/benchmark1 "$@" < "$MATRICES_FILE"
DAMN_CONFIG=32 run_benchmarks path/to/benchmark1 "$@" < "$MATRICES_FILE"
DAMN_CONFIG=32 run_benchmarks path/to/benchmark2 "$@" < "$MATRICES_FILE"
